Engineering field guide

Wellness Central, end to end

A plain-language map of every app, endpoint, and workflow in the Wellness Central platform — what it does, who uses it, and exactly which file it lives in. Written so a newcomer can follow it, and detailed enough that nothing is left out.

Five codebases make up the platform: a shared backend (Express/TypeScript + Azure Cosmos DB), a doctor portal serving both individual doctors and clinic staff, an admin portal for the platform's own operators, a pharmacy portal for medicine sellers, and a patient mobile app (Expo/React Native). This guide walks through all five.

Glossary

Six terms come up constantly in this guide. Knowing them up front makes everything else click faster.

SuperTokens
The self-hosted login system every app shares. It proves who someone is (their user ID) and tracks what roles they hold ("patient", "doctor", "admin", etc). It does not, by itself, know anything about clinics or appointments.
Cosmos DB
Microsoft Azure's NoSQL document database — the platform's single source of truth for almost everything. Instead of spreadsheet-style tables with fixed columns, each "container" (Cosmos's word for a table) just stores loose JSON documents. There are no joins between containers; related data is either duplicated or fetched separately and stitched together in code.
LiveKit
A hosted video/audio infrastructure service. It handles the hard parts of real-time video (WebRTC) so the platform's own code only has to hand out short-lived access tokens and connect to a named "room."
FHIR
("Fast Healthcare Interoperability Resources", said "fire") — an international standard for exchanging medical records between different healthcare systems in a common JSON shape.
requireRole()
A single backend gatekeeper function every protected API endpoint uses. It checks that a request carries a valid login session and that the caller holds one of the specific roles the endpoint requires.
EMR / EHR
EMR (Electronic Medical Record) is the clinical note for one single visit — what was discussed, prescribed, and recommended at that appointment. EHR (Electronic Health Record) is the patient's whole history — every past EMR, stitched into one timeline.

Shared login, one gatekeeper

All five apps authenticate against the exact same SuperTokens deployment — one flat pool of users, not five separate ones. SuperTokens itself runs as its own small service (wellness-platform/supertokens, a Docker image backed by Postgres), and the backend connects to it via backend/src/config/supertokens.ts.

The question everyone asks first

If patients, doctors, clinics, and admins all log into the same system, what stops a doctor's credentials from working on the patient app? Nothing at the login layer — SuperTokens only knows "this is user X, and X holds these roles." Roles are assigned at signup (a patient-app registration always adds the patient role; a clinic registration adds clinic_pending, and so on). The real wall is requireRole(), in backend/src/middleware/requireRole.ts — every sensitive API endpoint wraps itself in it, and it checks the caller's roles against whatever the endpoint requires. So a doctor's login token is technically valid on every app, but every patient-only endpoint would reject it, because "doctor" isn't in the list of accepted roles. (The patient app also does its own extra role check right after login, purely so it can show a friendly "no patient account found" message instead of a confusing empty dashboard.)

Roles used across the platform: patientdoctordoctor_pendingclinicclinic_pendingpharmacypharmacy_pendingadmin. The _pending variants exist because doctors, clinics, and pharmacies all go through an approval queue before they can act as the real thing — see Section 7 (Admin Portal) for how that queue works.

Two independent, finer-grained permission systems sit on top of roles, both following the same "default-allow, only an explicit no removes access" rule:

  • Clinic staff permissions (backend/src/utils/clinicScope.ts) — restrict what a branch-employee login can do inside the clinic portal: manage_doctors, manage_patients, manage_appointments, manage_schedules, view_analytics, manage_insurance, manage_payment. The clinic owner's own account always has every permission — this can only ever restrict a hired staff account.
  • Doctor self-service permissions (backend/src/utils/doctorPermissions.ts) — lets a clinic restrict what a doctor they employ can change about their own dashboard: manage_own_schedule, manage_own_profile, view_analytics, manage_account_settings.

The database: Cosmos DB

Cosmos DB is a NoSQL document database — worth pausing on for anyone used to spreadsheets or SQL. There's no fixed set of columns and no JOIN between tables; each "container" just holds a pile of JSON documents, and two documents in the same container can even have different fields. Every container also has a mandatory partition key — a field Cosmos uses to physically group documents together for fast lookups; querying across partitions (e.g. "every order that touches this one pharmacy," when orders are filed by patient) is explicitly slower and the code calls this out with comments wherever it happens.

Where it all runs

  • The backend is a two-stage Docker build deployed to Google Cloud Run (backend/Dockerfile, deployed via gcloud run deploy).
  • SuperTokens runs as its own small container (wellness-platform/supertokens/Dockerfile), independent of the backend.
  • The three Next.js portals (doctor, admin, pharmacy) have no Dockerfile or CI config of their own — consistent with each being deployed through Vercel's zero-config Git integration (push to main, Vercel builds and deploys automatically).
  • The patient app is built and shipped through Expo's own tooling, separate from the rest of the monorepo.
  • File storage (avatars, ID scans, prescriptions, lab/scan uploads) goes through Azure Blob Storage (backend/src/config/blob.ts), always as time-limited signed URLs rather than public links. Transactional email (OTP codes, etc.) goes through Resend (backend/src/config/resend.ts) — there is no SMS provider; every OTP is delivered by email. Push notifications ride on Expo's own push gateway (Section covers this again where relevant) rather than talking to Apple/Google directly.

02Video Calling — LiveKit

This is the most involved feature in the whole platform, so it gets the deepest treatment. Every online consultation — doctor and patient seeing each other face to face — runs through this system.

How LiveKit actually works

WebRTC is the browser/phone technology that lets two devices stream audio and video directly to each other with very low latency. Used raw, it's notoriously hard: negotiating a connection, working around firewalls, reconnecting after a network blip are all hard problems on their own.

LiveKit is a hosted service that wraps WebRTC and solves all of that. Instead of two devices connecting directly, everyone connects to a LiveKit media server, and it forwards each participant's audio/video to everyone else in the same room. Two concepts matter for reading the rest of this section:

  • Room — a named channel on the LiveKit server. In this platform, a room is one appointment's call, and the room's name is simply the appointment's own ID. LiveKit auto-creates a room the instant the first participant joins it — there is no separate "create room" step anywhere in this codebase.
  • Access token — a short-lived, signed permission slip ("this identity may join this room, and may publish/subscribe to audio, video, and small data messages"). Only a server holding the LiveKit API key + secret can mint one, which is why every call starts with a client asking the backend for a token — the frontend never holds the secret itself.

LiveKit also supports sending small binary messages to everyone in a room — its data channel. This platform leans on that constantly, for things well beyond video: in-call text chat, "a specialist wants to join," and "the doctor is proposing a follow-up appointment" all ride on this same mechanism, entirely separate from the camera/mic tracks.

Worth knowing

LiveKit itself has no concept of "appointments," "no-shows," or "doctors." Everything about appointment status, no-show detection, and waiting rooms described below is business logic this platform built on top of LiveKit's plain connect/disconnect events — tracked through ordinary REST calls to the Express backend, not anything LiveKit reports on its own.

Backend: rooms, tokens, and the no-show logic

backend/src/config/livekit.ts holds the API key/secret, and deliberately throws at startup if they're missing — no dev fallback, because a baked-in secret would let anyone reading the repo forge a token and eavesdrop on a live consultation. All of the actual call logic lives inside backend/src/routes/appointments.ts, interleaved with the rest of appointment booking.

The room name is just the appointment ID

When an online appointment is booked, the backend stamps livekitRoom: id straight onto the appointment document — the same human-readable ID used everywhere else (e.g. APT-20260819-DRSMITH-A3F9B2). There's no separate "room" entity to look up; the appointment is the room. In-person visits get livekitRoom: null.

Minting a token

GET /api/appointments/:id/livekit-token is what both doctor and patient call to get in. It checks the caller is genuinely one of the two parties on the appointment (403s everyone else), then builds a token scoped to exactly that room:

const at = new AccessToken(livekitApiKey, livekitApiSecret, {
  identity: userId,          // how LiveKit tells participants apart
  name:     participantName, // display name shown in the call UI
  ttl:      2 * 60 * 60,     // valid for 2 hours
});
at.addGrant({
  roomJoin: true, room: apt.livekitRoom,
  canPublish: true, canSubscribe: true, canPublishData: true,
});

A quirk worth noting: doctor and patient are handed different LiveKit WebSocket URLs (LIVEKIT_WS_URL_DOCTOR vs LIVEKIT_WS_URL_PATIENT) — a development-environment accommodation (doctor connects from a browser on the same machine as the dev LiveKit server, patient connects from a phone on the LAN), that in production would point both at the same real server.

Presence tracking — the real heart of the feature

There is no LiveKit webhook anywhere in this backend (confirmed by searching every route file). Instead of trusting LiveKit's own server-side events, the app rolls its own presence system: both doctor and patient apps call PATCH /api/appointments/:id/call-presence with { inCall: true } the moment their own connection succeeds, and { inCall: false } on disconnect. This single endpoint is what decides, after the fact, whether a call actually happened:

  1. Race-safe writes: Cosmos optimistic-concurrency (ETag) with a retry loop, so near-simultaneous doctor/patient updates can't silently clobber each other.
  2. callStartedAt is stamped the first moment both sides are simultaneously inCall: true — proof a real call happened.
  3. When both sides have since left: if callStartedAt was ever set → appointment becomes completed. If it was never set (the two sides were never in the room together) → appointment becomes cancelled with cancelledReason: "no_show".
  4. The first time the doctor's presence flips true, a push notification goes to the patient ("Dr. X has joined — please join soon to avoid a no-show cancellation") — the only real nudge, since there's no hard timer.
A real architectural trade-off

Because there's no server-side webhook, the completed-vs-no-show decision depends entirely on each client faithfully calling call-presence on both connect and disconnect. If an app crashes mid-call without running its cleanup step, that update never arrives. The only backstop is a lazy end-of-day sweep — autoExpireStaleAppointments() in backend/src/utils/appointmentSweep.ts — which runs every time anyone lists their appointments, and auto-cancels anything still scheduled/in_progress once its calendar day has fully passed.

Two more presence-style signals worth knowing: PATCH /:id/waiting (patient pings this the moment they open the waiting-room screen — powers the doctor portal's "Online Now" list, independent of whether a call has started), and PATCH /:id/status (only the primary doctor can set this; the doctor portal fires status: "in_progress" automatically the instant their own LiveKit connection succeeds — this is exactly what unlocks the patient's "Join Call" button, described below).

Inviting a specialist mid-call

A primary doctor can pull a second doctor into an ongoing call. POST /:id/invite-specialist mints the specialist a token for the same room and pushes a specialist_invite message over the LiveKit data channel so the patient's consent modal pops up live, with no polling. The patient answers via POST /:id/specialist-respond (also echoed back over the data channel); the specialist actually joins via GET /:id/specialist-join.

Proposing a follow-up

Mid-call, the doctor can propose a follow-up date/time (POST /:id/send-followup), sent to the patient over the same data channel. If the patient accepts (POST /:id/followup-respond), a brand-new appointment document is created immediately — with its own fresh livekitRoom — and a followup_accepted data message (or followup_declined) is sent back into the room so the doctor's screen updates live.

Doctor portal: the consultation screen

The doctor's live-call screen is doctor-portal/app/appointments/consult/page.tsx — reached by clicking "Connect Now" from the Waiting Room (doctor-portal/app/appointments/waitingroom/page.tsx; a similarly-named but misspelled folder, app/appointment/waitigrrom, is kept only as a redirect for old links). A near-identical screen, doctor-portal/app/video-calls/page.tsx, is used exclusively by an invited specialist joining an existing call, not the primary doctor.

On mount, it builds a livekit-client Room, requests a token, connects, then immediately fires call-presence: true and status: in_progress. While connected, the doctor can: toggle mic/camera; use an in-call Chat tab (ephemeral — LiveKit data messages only, never saved, gone once the call ends); fill out the EMR tab (the structured clinical note — saved via POST /:id/emr, a completely separate, persisted system from the ephemeral chat); open a read-only EHR side panel (the patient's full history, plus any linked external FHIR data — Section 4); invite a Specialist; or propose a Follow-up.

Ending the call: if the patient is still connected, a confirmation modal appears first ("The patient is still in the call") to prevent an accidental hang-up. Confirming disconnects LiveKit and reports call-presence: false, which is what lets the backend's completed/no-show logic run.

Patient app: waiting room and in-call screen

Files: app/waiting-room.tsx → app/video-call.tsx → app/call-paused.tsx (if things go sideways) → app/rate-experience.tsx. The LiveKit SDK itself is wrapped defensively in utils/LiveKitMobile.tsx, which try/catch-guards the native import and falls back to a harmless no-op stub if the native WebRTC module isn't available (e.g. running in plain Expo Go) — so a missing native module degrades gracefully instead of crashing the whole app.

The waiting room pings PATCH /:id/waiting on mount, then polls the appointment every 5 seconds. Critically, the "Join Call" button stays disabled and grey until status === "in_progress" — which, recall, only becomes true the instant the doctor's own connection succeeds. This structurally prevents a patient from ever walking into an empty room.

Once in the call, leaving has three distinct, deliberately different paths:

  • The doctor leaves first — the patient is routed straight to the rating screen (there's no one left to talk to).
  • The patient taps End while the doctor is still connected — instead of ending outright, they're routed to call-paused.tsx ("Dr. X is still in the call — Rejoin?"), specifically to catch accidental hang-ups or network blips without prematurely ending a consult the doctor is actively running. From there, "Rejoin" reconnects cleanly; "End Consultation" (or the doctor also leaving in the meantime, which this screen polls for) forwards to the rating screen.
  • An invited specialist leaves (not the primary doctor) — the patient just sees a toast and stays in the call.

Every exit path reports call-presence: false as its cleanup step — the trigger for the backend's completed/no-show decision described above.

A full call, start to finish

  1. Booking. Patient books an online visit; the appointment is created with livekitRoom already set to its own ID.
  2. Waiting room. Patient opens the waiting-room screen, marks themselves present, and starts polling for the doctor.
  3. Doctor connects. Doctor clicks "Connect Now" — this is the moment the LiveKit room is actually created on the server, since the doctor arrives first. status flips to in_progress.
  4. Patient's button unlocks. The patient's next poll sees in_progress and enables "Join Call."
  5. Patient connects. Both sides are now in the same room; LiveKit begins forwarding audio/video. callStartedAt is stamped the instant both are simultaneously present.
  6. In-call. Video tiles render, mic/camera toggle, ephemeral chat, optional specialist invite or follow-up proposal — all riding on the same LiveKit data channel.
  7. Doctor ends. Both sides report call-presence: false; since callStartedAt was set, the appointment becomes completed.
  8. Post-call. Patient rates the experience, then sees a summary sourced from whatever EMR the doctor saved during the call.

Two edge cases worth naming explicitly: if the doctor connects and later leaves without the patient ever joining, callStartedAt was never set, so the appointment is marked cancelled — no-show instead of completed. If neither side ever joins at all, the call-presence logic never fires either way — that's what the end-of-day autoExpireStaleAppointments() sweep exists to catch, marking it cancelled — auto_expired.

03Chat & Messaging

The platform runs two completely separate chat systems that happen to share the same transport technology but never mix data — plus one unrelated AI screen that just happens to share a name with one of them.

Patient ↔ Doctor chat

The clinical conversation between a patient (or a family-member profile) and a doctor they have an appointment with.
backend/src/routes/messages.ts · Cosmos container messages

Clinic staff chat

An internal-operations chat between a clinic owner, that clinic's branch staff, and the doctors on that branch's roster.
backend/src/routes/clinicMessages.ts · Cosmos container clinicMessages

They're deliberately kept in separate Cosmos containers with different conversation-ID prefixes (chat:... vs staffchat:...) specifically so a query bug in one system could never leak the other's data.

Not the same thing

The patient app also has a screen literally named app/chat.tsx — but it isn't doctor messaging at all. It's a Gemini-powered AI wellness assistant (POST /api/wellness/chat) that helps a patient describe symptoms and, if warranted, walks them toward booking a real doctor. Real doctor chat lives in app/doctor-chat.tsx and app/message-doctor.tsx instead.

How "real-time" actually works here

Neither classic WebSockets nor polling — the platform reuses LiveKit's data channel (the same one that carries in-call chat and specialist/follow-up signaling during video calls) as a lightweight real-time bus for persisted chat too. The flow is identical on both sides:

  1. Load history. A normal REST call (GET /api/messages/:conversationId) reads saved messages from Cosmos.
  2. Get a token. GET /api/messages/token?channel=chat:{profileId}:{doctorId} mints a LiveKit token scoped to a room named after the conversation.
  3. Connect and listen. The client joins that LiveKit room purely for its data channel, listening for chat_message packets.
  4. Sending a message always writes to the backend first (POST /api/messages/:conversationId — the durable source of truth), then re-broadcasts the same message over the data channel so the other party sees it appear instantly if they're currently connected. If they aren't connected right now, they simply see it the next time they open the conversation — there's no server-side push through LiveKit itself.

Who can message whom

Patient-doctor chat is gated to an existing appointment: the backend's hasAppointment() check (in messages.ts) requires a non-cancelled appointment between that specific profile and that doctor before a token or message will be accepted — a patient can't cold-message an arbitrary doctor. The patient app mirrors this visually in app/message-doctor.tsx, splitting "Your Doctors" (tap to chat) from "Other Doctors" (tap prompts "Book Appointment First"). Clinic staff chat instead enforces a strict role-pair whitelist (org owner ↔ their own staff; staff ↔ doctors on their own branch; staff ↔ their own owner) — no direct owner↔doctor or cross-branch chats.

What's tracked, and what isn't

  • Read receipts: yes, simply — opening a conversation (GET /:conversationId) marks the other party's messages read as a side effect. There's no per-message delivery/read tick shown in the UI.
  • Attachments: no. Every message document and every chat UI is text-only.
  • Push notifications on a new message: not implemented. Neither messages.ts nor clinicMessages.ts calls the push-notification helper that other features (like appointment events) use — a user only learns of a new message by having the chat screen open, or later noticing the unread badge.

04FHIR — Exchanging Records With the Outside World

What FHIR is, in plain terms

FHIR (Fast Healthcare Interoperability Resources) is an international standard that lets different healthcare systems — a hospital's own EHR, a lab system, an insurer, a telehealth app like this one — exchange a patient's clinical data without every vendor inventing its own incompatible format. The core unit is a resource: a standardized JSON shape for one kind of clinical fact. A Patient resource holds demographics; an Encounter is one visit; an Observation is one measurement (a vital sign, a lab result); a Condition is a diagnosis; a MedicationRequest is a prescription.

Honest scope, up front

This is a read-only client that fetches FHIR resources from an external server and displays them alongside the platform's own native records — it does not generate FHIR resources from this platform's own data for anyone else to consume. If you're picturing "this platform exports its own patients as FHIR," that isn't what's built; the direction is inbound only, pulling in a patient's external history from elsewhere.

Today, "elsewhere" is the public HAPI FHIR R4 sandbox (https://hapi.fhir.org/baseR4) — explicitly a stand-in, per code comments, for the clinic's real "Cortex" EMR once production credentials exist (backend/src/config/fhir.ts). A patient's Cosmos record carries an optional fhirPatientId linking them to a record on that server; the backend queries it live, on every page load, with no caching.

What's actually covered

Read (consumed): PatientEncounterObservationDocumentReferenceCompositionConditionMedicationRequest — 7 of the dozens of standard FHIR types. Not covered at all: Procedure, AllergyIntolerance, Immunization, DiagnosticReport, CarePlan, insurance-related resources, bulk export, or subscriptions. There's no validation against the FHIR spec, and no authentication to the FHIR server yet (fine for a public sandbox; flagged in code comments as needing OAuth2/SMART-on-FHIR before pointing at a real EMR).

Linking a patient to an external record is currently a manual, one-off developer action — a CLI script (backend/src/data/seedFhirDemo.ts), not anything reachable from the product UI.

Where the logic lives

backend/src/services/fhirClient.ts is the low-level HTTP client (handles pagination, parses FHIR error bodies). backend/src/services/fhirService.ts turns raw FHIR JSON into simple display shapes — the closest thing to a "mapping layer" in the codebase, but note it maps FHIR → internal display shape, the opposite direction of a true export feature.

05Backend API Reference

Around 50 route files live in backend/src/routes/, each wired up in backend/src/index.ts. They're grouped below by who calls them. Click any file to expand its full endpoint list — every one of them requires a valid login (verifySession) unless stated otherwise, and most also require a specific role via requireRole(...).

Patterns that repeat everywhere

Approval queues — doctors, clinics, pharmacies, pharmacy products, insurance policies, and fee changes all follow the same shape: a status field starting at pending, an approve/reject endpoint, and (for accounts) a SuperTokens role that flips in lockstep (e.g. doctor_pending → doctor). Soft-delete, never hard-delete — removing a doctor or deactivating a patient just flips a status field (so appointment history survives) and calls SuperTokens' revokeAllSessionsForUser so any already-open session dies immediately. Never trust the client for money or authorization fields — an appointment's price, an insurance policy's verified status, and the payment method for in-person visits are always resolved or re-checked server-side, regardless of what the client sends.

A quiet anti-fraud detail

PUT /insurance never trusts a client-supplied policy status — any brand-new entry, or one whose provider/policy-ID/plan changed, is force-reset to pending server-side; an unchanged entry keeps whatever admin already verified. A patient can never self-approve their own insurance.

In-person visits are always pay_at_clinic (server-forced); insurance payment is only accepted if the policy is active and actually matches one of the doctor's clinic's accepted policies; the price is always resolved server-side from the doctor's fee, never trusted from the client. Generates a human-readable ID like APT-20260819-DRSMITH-A3F9B2.
  • GET/, /doctor, /doctor/tasks, /:id — listings/lookups per role
  • PATCH/:id/cancel — role-aware, notifies whichever party didn't initiate it

How the EMR survives a multi-doctor consult

Medicines and labs are tagged with a contributorDoctorId so a specialist's additions never wipe the primary doctor's entries — saving replaces only this doctor's own tagged entries and keeps everyone else's untouched. Free-text sections are shallow-merged the same way. Addenda are strictly append-only, timestamped and signed at write time — a correction is always a new addendum, never an edit, mirroring real EMR audit-trail conventions.

  • POST/chat — the "Dr. Wellness" AI assistant, system-prompted to refuse off-topic questions and append a hidden marker when it thinks the patient should book a real doctor (the frontend turns that into a booking prompt)

  • CRUD /food-log, /exercises, CRUD /workout-log (+ /workout-log/bulk) — calories burned computed from the patient's own logged body weight

menstrual.tsCycle prediction engine — the most algorithmically sophisticated module in the platform
  • Cycle math: ovulation is placed a fixed ~14 days before the next predicted period (the luteal phase is biologically the stable part of a cycle, not the follicular phase); the fertile window is ovulation −5 to +1 days, matching real sperm-survival biology
  • Cycle-length learning: takes the median gap between logged period start dates (robust to one outlier month), only counting gaps in the plausible 18–60 day range
  • Irregularity detection trips on any of three independent signals: a single gap outside 21–35 days, more than a 9-day spread between the shortest and longest gap, or a standard deviation above 7 days across gaps
  • BBT ovulation confirmation: scans daily basal body temperature for a sustained rise of ≥0.2°C above the prior 6-day average, held 3+ consecutive days — a genuine fertility-tracking technique, not a guess
  • GET/insights — the full computed payload (phase, predicted dates, irregularity flag, BBT-confirmed ovulation if available); recomputed fresh on every read, never cached
pregnancy.tsPregnancy tracking, including a gestational-diabetes sub-log

  • GET/PUT /log, GET/log/history — daily mood/symptoms/weight/water/pill-tracker log
  • POST/scan — ultrasound/scan image or PDF upload, replacing any prior scan for that date
  • PUT/DELETE /diabetes — nested gestational-diabetes log merged into the same day's document

06Doctor Portal

One Next.js codebase, two audiences: individual doctors under app/dashboard/*, and clinic owners/staff under app/clinic/*. Shared auth screens live under app/auth/*, and the consultation itself under app/appointments/* (covered in depth in Section 2). Every screen talks to the backend through doctor-portal/lib/apiFetch.ts, a fetch wrapper that attaches the SuperTokens token and silently retries once after a session refresh if a request comes back 401.

Shared auth & onboarding

There's no self-serve doctor signup anywhere — a doctor account is always created by a clinic (Add Doctor wizard, below). Only clinics register themselves:

  1. Register a clinic — app/auth/signup/page.tsx, a 5-step wizard: verify email/phone → OTP → basic details → create password → success. Registering doesn't establish a session by itself, so the last step immediately signs in with the same credentials before handing off to the profile wizard.
  2. Complete Profile — app/auth/complete-profile/page.tsx, a second, longer wizard: owner's personal info → accepted insurances → company info (license, address, logo, payment settings) → weekly availability. A "Do you operate additional branches?" prompt loops the company-info + availability pair again per extra branch. Ends with an "awaiting admin review" message.
  3. Login — app/auth/login/page.tsx. After a successful sign-in, the app reads the session's roles and branches: an unfinished clinic_pending account goes back into the profile wizard; a finished one goes to an "awaiting approval" screen; an approved clinic goes straight to /clinic; a doctor with 2FA enabled is routed to a one-time code screen first.

Password reset (app/auth/forgot-password → reset-otp → reset-password) is a shared three-step OTP flow used by both doctors and clinics. Two-factor login (app/auth/two-factor) is not self-service for doctors — a doctor can never turn their own 2FA on or off; only the employing clinic can, from that doctor's detail page.

The appointment lifecycle, doctor's-eye view

  1. Scheduled. Booked by a patient; appears on the Dashboard, the Appointments hub (app/appointments/page.tsx), and Schedules.
  2. Pre-visit review. If the patient filled in a questionnaire, the doctor can review it (app/appointments/previsit-form/page.tsx) before starting.
  3. Waiting room. Shows which patients have actually signalled they're present, distinct from just "scheduled."
  4. In-progress. Online visits open the LiveKit call screen (Section 2); in-person visits open app/appointments/complete-emr/page.tsx directly instead — since there's no video call, opening this screen is the doctor starting the visit, and it flips status to in_progress itself.
  5. Completed. Moves into the Patients directory, Analytics revenue, and — if no EMR was ever saved — resurfaces as a "pending EMR" task.

Feedback splits clinic reviews from per-doctor reviews, with an optional clinic reply thread. Messages and Help mirror their doctor-side counterparts, scoped to the clinic's own staff/doctors.

app/clinic/accounts/page.tsx"User Roles" — where the whole permission system from Section 1 is actually administered

Three tabs — Branches, Doctors, Staff. Selecting a doctor or staff account opens an "Access" panel with the relevant permission toggles (the 7-key staff set or the 4-key doctor set from Section 1), saved individually or, for a whole branch at once, via a "Save for all users" bulk action. Reachable only by the org owner — a branch-staff account sees a plain "available to the clinic owner" message instead.

07Admin Portal

The platform's own control tower — used by Wellness Central's own staff, not any clinic. Every dashboard page is wrapped in a route guard that re-verifies the session against the backend on mount, so a stale cached token alone is never trusted. The sidebar covers eighteen sections; grouped by purpose below.

Onboarding queues — the platform's core approval workflow

Five separate domains — Clinics, Doctors, Pharmacy, Fee Requests, and Insurance Verifications — all follow the identical two-tab shape: a pending queue and an approved/history list, with Approve and Reject (the latter always capturing a typed reason shown back to the submitter).

Clinics nested approval

Onboarding queue plus a five-step "Add Clinic" wizard for admin-initiated onboarding. Multi-branch orgs get a second, nested approval layer — each additional branch is reviewed independently of the parent org.

Doctors schedule review

Six-step Add Doctor wizard. A doctor's detail page shows an amber banner whenever they've edited their own availability post-approval, with a one-click "Verify Now" to promote the pending schedule to live.

Pharmacy two-level

Pharmacies and their individual products are approved independently — a pharmacy can be live while a specific new product it added still waits for review.

Fee Requests & Insurance side-by-side diff

Both show the old value against the requested new one directly side by side before an admin decides — old consultation rate vs. new, or an unverified policy's details as submitted.

Directories & oversight

PatientsFull clinical record access, platform-wide — the most sensitive screen in the app

A patient's profile page gives an admin unrestricted read access to every clinical note across every doctor that patient has ever seen — reason for visit, exam findings, prescribed medicines, doctor addenda, the works — for support/dispute purposes. The one action available is deactivate/activate, which (as covered in Section 5) also revokes every active session immediately.

Pharmacy inventory, Lab Service, VaccinationCatalogue and stock oversight — three slightly different models

Pharmacy stock supports a Flag/Unflag action per product — content moderation that hides a listing without deleting it, preserving history. Lab Service has no approval queue at all in the UI — new labs go live immediately, since these are platform-authored catalogue entries, not third-party submissions being vetted. Vaccination is likewise a straight catalogue editor with a live-preview pane mirroring exactly what the patient app will render.

Emergencies, Feedback, SupportRead/respond oversight screens

Emergencies is a read-only monitor of the SOS feature (Section 5) — the actual verification happens doctor-side; admin just watches. Feedback aggregates every rating platform-wide with no moderation action attached. Support is the admin-facing helpdesk inbox — status toggle, a threaded comment view, and a separate "official reply" field distinct from the ongoing comment thread.

Finance, content & internal access control

Earnings, OrdersFinancial and fulfillment oversight

Earnings — only the Consultations tab is wired up; Pharmacy, Lab, and Radiology tabs are explicit "Coming Soon" placeholders. Orders — a status-pipeline dropdown lets admin walk any pharmacy order through confirmed → processing → shipped → delivered or cancel it directly.

RolesInternal RBAC — for doctors and patients too, not just other admins

Three tabs (Doctors / Patients / Admin), each toggling four flags: medicalRecords, prescription, emrUpdates, systemConfig. This is a separate, coarser system from the clinic/doctor permission model in Section 1 — worth not conflating the two when reading the codebase. Toggles are staged as a draft and only committed on explicit Save, with an "unsaved changes" guard if the admin tries to switch users mid-edit.

ArticlesThe CMS behind the patient app's wellness content library

Standard CRUD plus Flag/Unflag (hides from the patient app without deleting) and a one-time "Seed Articles" developer convenience that bulk-creates sample content if the library is empty.

Activity LogThe platform-wide audit trail, browsable

Every meaningful action across admin, doctor, patient, pharmacy, and lab sources is expected to land here — filterable by source and a coarse time window. Purely read/browse; no action is taken from this screen. This is the same log every logActivity() call in the backend writes into.

SettingsTen configuration panels — some live, some deliberately not yet

Backend-connected: admin's own profile, general defaults, notification preferences, appointment rules (max bookings/day, cancellation-notice window), maintenance/backup scheduling, security settings (password-expiry policy and the admin's own 2FA toggle — the same OTP flow used at login once enabled), and Privacy Policy/Terms document uploads.

UI-only placeholders (explicit in code comments — no backend calls at all yet): Platform Fee Management (per-specialty commission editor), Payments (withdrawal frequency, primary bank account), and Insurance Providers (enable/disable toggles per insurer). Worth knowing these look finished but don't persist anything.

Two front-end-only screens worth flagging

Forms builder — designed, not shipped

The Forms section (app/dashboard/forms/*) is a fully-built, genuinely impressive drag-and-drop form designer — 14 field types, a live canvas, a properties panel — but none of its three pages make a single network call. The list is a hardcoded array; "Save Changes" just navigates back without persisting anything. There is no adminForms.ts backend route. Treat it as a designed-but-unwired feature, likely intended for custom pre-visit intake forms.

08Patient App

Built with Expo/React Native and file-based routing under app/ — this is the only piece of the platform living in a separate repository. One idea threads through almost every screen here, so it's worth stating up front.

The idea that shapes everything below

A patient can add up to 4 family members (5 profiles total, self included) and switch which one is "active" from anywhere in the app — handled by context/ActiveProfileContext.tsx. Nearly every screen that shows or edits personal data threads an optional profileId/memberId through its API calls for exactly this reason: viewing allergies, booking an appointment, checking notifications, or editing a photo all need to know which of the account's profiles is currently in view.

Onboarding & auth

Splash → 3-slide walkthrough → email/phone entry (app/onboarding/login.tsx) → password (email-login.tsx, a raw fetch to /auth/signin rather than the SDK's own sign-in call, followed by a role check confirming the account actually holds the patient role — since the shared login tenant means a doctor's or clinic's credentials would otherwise sign in here too). Registration (register.tsx → OTP → enter-otp.tsx, which is what actually calls POST /patients/register) leads into a 4-step profile wizard: complete-profile → allergies → medications → chronic-diseases, each save-able or skippable, each reused later for onboarding a new family member by passing a memberId. 2FA login and password reset are separate three/four-step OTP flows mirroring the doctor portal's pattern.

Home, search & booking

app/(tabs)/index.tsxHome — personalized around whichever profile is active

Search bar, quick-links grid, top clinics, and a "Health Guides" carousel that's re-ranked client-side per the active profile — a pure scoring function boosts articles by gender, pregnancy status, chronic conditions, and age (a diabetic profile sees diabetes content scored higher, a pregnant self-profile sees Pregnancy content boosted). Switching the active profile reshuffles the whole list.

search-doctors.tsx · doctor-profile.tsx · clinics.tsx · clinic-profile.tsxFinding a doctor or clinic

Free-text search is layered with a symptom-to-specialty map — typing "chest pain" surfaces cardiologists even though no doctor record mentions the symptom directly. Doctor and clinic profiles show live stats, ratings, and availability pulled straight from the backend.

new-appointment.tsx → payment-options.tsx → appointment-booked.tsxThe booking flow itself

Choose "For Me" or a family member, state the reason for visit, then payment-options.tsx — the one checkout screen in the whole app with real insurance matching: it fetches the doctor's clinic's accepted policies and cross-references the patient's own verified ones, offering only genuine matches. Confirming here is what actually calls POST /api/appointments; every other purchase flow in the app (pharmacy, lab, vaccination) creates its order/booking on its own separate payment-options screen instead.

pre-visit-form.tsx · waiting-room.tsx · video-call.tsx · rate-experience.tsx · diagnostics-medication.tsxThe consultation itself and what follows it

Pre-visit intake, waiting room, and the video call itself are covered in full in Section 2. After the call: rate-experience.tsx resolves the reviewer's identity directly via SuperTokens rather than the app's usual context, specifically to sidestep a timing race right after a call ends. diagnostics-medication.tsx is the "here's your prescription" screen — it polls the appointment up to 8 times, 3 seconds apart, waiting for the doctor's saved EMR to appear, showing "Checking for prescription…" in the meantime rather than a dead end.

Appointments & records

app/(tabs)/doctors.tsx — the Doctors tab: recent doctors plus an Upcoming/Past/Cancelled appointment list for the active profile. app/my-records.tsx — searchable past-visit history, with a rich welcome state and suggested doctors for a brand-new user. app/record-detail.tsx — one appointment's full record: chief complaint, doctor's notes, prescriptions, lab orders, payment — plus, when linked, the external FHIR section from Section 4.

Profile & family members

(tabs)/profile/index.tsx · details.tsx · personal-info.tsx · edit-personal.tsxThe profile home and the "who am I editing" chain

The Profile tab shows a "Viewing [X]'s profile — not yours" banner with a "Switch back" link whenever a family member is active — a deliberate guard against silently editing the wrong person's data. The account owner's email is locked here (it's their login credential, shown but read-only); a family member's email is a normal editable field, since members have no login of their own.

family.tsx · add-member.tsx · allergies.tsx · medications.tsx · chronic-diseases.tsx · drug-details.tsxManaging the household

A grid of profiles with an "Add" tile, enforcing the 4-additional-members cap client-side before even opening the add form. Adding a member reuses the exact same allergies/medications/chronic-disease onboarding screens from initial signup, scoped by a memberId param. drug-details.tsx is a per-medication accordion editor (dosage, frequency, start/end dates) that saves back into the same medications object.

insurance.tsx · wallet.tsx · reminders.tsx · support.tsx · raise-issue.tsx · settings*.tsxEverything else under Profile
  • Insurance — add/view policies grouped Active / Waiting / Rejected; every new entry starts pending, since only an admin can verify one (Section 7).
  • Wallet — balance + transaction history, account-level (not per-family-member).
  • Reminders — a month calendar for medication reminders, with an add/delete modal.
  • Support / Raise an Issue — the same ticket system used platform-wide (Section 5), with photo attachments.
  • Settings — Account — change password, 2FA toggle, active-sessions list, sign-out-everywhere, and account deletion: deleting the whole account cascades to every family member automatically (they're sub-records, not separate accounts); deleting a single member leaves the account untouched and switches the active profile back to self. Settings — Notifications / Privacy / Language round out the section.

Buying medicine, booking tests, booking vaccinations

Three parallel commerce flows under app/(buy-medicines)/*, app/lab-booking/*, and app/vaccination/* — each shaped the same way: browse a public catalogue → assign items to one or more patients (self or family members, up to 6) → set a preference (home visit vs. in-clinic, for lab/vaccination) → a dedicated payment-options screen → a success screen → a detail/tracking screen.

Pharmacy

The only flow with a real prescription-verification step (add-prescription.tsx — upload a photo, or look up by eRx number/Emirates ID, the latter two currently simulated with a timeout rather than a real backend check). Three dedicated failure screens (expired / unclear / unverified) each offer "Try Again" or "Consult a Doctor" instead of a dead end.

Lab tests

A test flagged requires_doctor_approval routes the flow through an extra consultation-time picker before checkout — DOH/DHA/MOH-style compliance messaging appears inline on the test's detail page.

Vaccination

The booking call itself happens on the success screen rather than the payment screen, guarded by a useRef so it can never fire twice even on a re-render — a deliberate defense against double-booking.

Payment is mocked everywhere

Every "credit card" list across all four checkout flows (appointments, pharmacy, lab, vaccination) is a static, fake array — there is no real payment gateway anywhere in this codebase. Selecting a card and confirming simply marks the order paid server-side. Insurance is the one exception with real logic behind it, and only on the appointment-booking flow — the pharmacy/lab/vaccination checkouts still show a hardcoded insurance list rather than the patient's actual saved policies.

Wellness, fitness & cycle tracking

app/(tabs)/wellness.tsx is the hub, fanning out into three substantial sub-systems, all under app/wellness/*:

  • Fitness & nutrition — a questionnaire computes calorie/macro targets client-side (TDEE formula) on first use, then a dashboard tracks food (search or AI photo-scan via the Gemini endpoint from Section 5), workouts (routine library or free exercise logging, with a live timed logging screen), and weight, all readable as daily/weekly summaries.
  • Menstrual tracking — the richest UI wrapper around the cycle-prediction engine described in Section 5: a calendar, a forecast timeline, 90-day trend charts, symptom pattern analysis, and phase-specific self-care tips.
  • Pregnancy tracking — due-date setup, a gestational-age dashboard, daily symptom/mood logging, a scan-report photo upload, a dedicated gestational-diabetes tracker, and week-by-week educational content (purely local, no network call).
  • Assessments — a quiz system (BMI, pain scale, dietary habits, etc.) that produces a risk-level result with recommended labs and doctors matched to the outcome.

Articles, SOS, notifications

Articles (app/articles/index.tsx, app/article/[id].tsx) share the same profile-aware ranking used on Home. SOS (app/sos.tsx → app/emergency-code.tsx) is a press-and-hold button generating the 15-minute emergency code from Section 5, with an explicit warning to share it only with a real medical responder. Notifications (app/notifications.tsx) has an All/Unread filter and scopes "Mark all read" to the currently active profile specifically, so switching to a family member and clearing their notifications never silently clears the account owner's own unread ones too.

Reviews

There's no standalone "leave a review" screen — rating collection is embedded as a post-transaction step in three places, all posting to the same POST /api/feedback endpoint with a folder discriminator: rate-experience.tsx (post-call, folder: "appointment"), the pharmacy order-success/summary screens (folder: "pharmacy"), and the lab-booking success screen (folder: "lab").

09Pharmacy Portal

The staff-facing back office for pharmacies fulfilling the medicine orders patients place through the app's buy-medicines flow. A fully-built Next.js app — not a stub — running on its own at wellness-platform/pharmacy-portal.

Registration is self-serve (app/auth/register/page.tsx, a 3-step wizard) but gated: a new account holds pharmacy_pending and sits on a holding screen ("Application Under Review") until an admin approves it in the Admin Portal (Section 7), at which point the role flips to pharmacy.

Why the backend has two files for "pharmacy"

backend/src/routes/pharmacy.ts is this portal's own router (requireRole("pharmacy")) — plus two public catalogue endpoints the patient app calls directly. backend/src/routes/medicineOrders.ts, despite sharing the same /api/pharmacy base path, is the patient app's router (requireRole("patient")) for placing and tracking orders. The pharmacy portal never calls anything in medicineOrders.ts, and the patient app never calls the staff-only routes in pharmacy.ts — same URL prefix, two entirely separate audiences.
